# Как искать: команды и разбор находок

Этот документ отвечает на вопрос «какую команду набрать и что делать с выводом».
Его открывают на каждой записи. Обоснования — почему ступени в таком порядке, как
`route` превращается в файл — лежат в `algorithm.md` и читаются один раз.

Всё, что здесь описано, делается **вами**: скрипта в этой версии скилла нет.

---

## 0. Разведка репозитория — один раз, до первой записи

Занимает минуту и снимает главный источник ошибок: поиск «там, где нашлось прошлый
раз». Четыре вопроса, на каждый — команда и что считать ответом.

### Есть ли выделенный контент-слой

```bash
ls src/shared/config/ src/content/ content/ data/ src/data/ 2>/dev/null
```

Папка есть — почти весь прозаический текст лежит там, и поиск в первую очередь идёт
по ней. Папки нет — тексты размазаны по компонентам, доля автоприменения будет ниже,
и это ограничение репозитория, а не дефект работы (PRD, раздел 12).

### Как устроены маршруты

```bash
ls src/routes/ src/pages/ app/routes/ 2>/dev/null
```

Папка `routes/` с файлами вида `tarify.tsx`, `products.$id.tsx` — файловая
маршрутизация. Пусто — ищите конфиг маршрутов:

```bash
rg -l 'createRoute|createBrowserRouter|createFileRoute|path:' src/ | head
```

Здесь регулярное выражение уместно и `-F` не ставится: ищется одно из нескольких
имён, а не чужой текст. Правило «всегда `-F`» из раздела 2 относится к поиску
содержимого `was`, где спецсимволы приходят снаружи и нам не подконтрольны.

Разбор трёх раскладок и что делать с динамическими сегментами — `algorithm.md`,
раздел «`route` → файл».

### Есть ли словари локализации

```bash
rg -l "useTranslation|i18n|\bt\(['\"]" src/ | head
rg --files -g '*.json' src/locales src/i18n locales 2>/dev/null | head
```

Нашлось — значит часть текста в исходниках отсутствует как текст: там ключи.
Это класс недостижимого текста, см. SKILL.md.

### Какие расширения в ходу

```bash
rg --files -g '*.{ts,tsx,js,jsx}' src/ | wc -l
rg --files -g '*.{vue,svelte,astro,mdx}' src/ | wc -l
```

Ответ нужен, чтобы задать `-g` в командах ниже и не искать в том, чего нет.

Здесь и всюду дальше используется `rg --files`, а не `fd`: `fd` в системе может
не стоять — проверено, на машине разработчика его не оказалось, — а `rg` нужен
для поиска в любом случае. Инструмент, которого нет, даёт пустой вывод, и разведка
молча отвечает «таких файлов ноль» вместо «команда не сработала».

## 1. Область поиска

**Всегда исключаются:** `node_modules`, `dist`, `build`, `.output`, `.next`,
`coverage`, `.git`.

### И отдельно — документация, которая цитирует контент

Планы, спецификации и записи разбора внутри репозитория часто содержат **тот же
текст, что и контент-слой**, слово в слово, внутри кодовых блоков. Такой файл
даёт фантомного кандидата на каждую запись и делает однозначный случай похожим
на дубликат.

Это не гипотеза. На прогоне (прототип `IS_Landing`, ревизия `a3e7252`) один
файл — `docs/superpowers/plans/2026-09-02-redesign.md`, 3505 строк — дублировал
**105 из 283 длинных литералов контент-слоя, 37%**. Он всплывал почти в каждом
поиске первой же строкой.

Поэтому на разведке (раздел 0) добавляется пятый вопрос:

```bash
rg --files -g '*.md' -g '!node_modules' | head -20
```

Нашлись планы, спеки, отчёты, `CHANGELOG` — **исключайте их из поиска**:

```bash
rg -n -F "ФРАГМЕНТ" -g '!node_modules' -g '!dist' -g '!docs' -g '!*.md'
```

> **Сначала проверьте, не рендерится ли markdown как контент сайта.**
> Если проект собирает страницы из `.md` (MDX, `remark`, папка `content/*.md`),
> то markdown — это и есть исходники, и исключать его нельзя. Проверка:
> ```bash
> rg -l 'mdx|remark|markdown' src/ vite.config.* next.config.* 2>/dev/null
> ```
> Пусто — markdown в сборку не входит, исключайте смело. На прогоне было пусто.

Тесты (`tests/`, `*.spec.ts`, `*.test.ts`) из поиска **не исключаются**: находка
в тесте отбрасывается чтением (раздел 4), но сам факт, что текст закреплён тестом,
полезно знать — правка сломает этот тест, и об этом стоит сказать в отчёте.

`ripgrep` уважает `.gitignore` и делает это сам — но только если папки в `.gitignore`
перечислены. Проверять не нужно, надёжнее задать явно:

```bash
rg -n --fixed-strings "ФРАГМЕНТ" \
  -g '!node_modules' -g '!dist' -g '!build' -g '!.output' -g '!.next' -g '!coverage'
```

Почему исключение обязательно, а не желательно: строка, найденная в `dist/`, — это
**наша же строка после сборки**. Правка туда не доедет до исходников, а следующая
сборка её сотрёт. Хуже того, находка в `dist/` выглядит как успех и добавляет
кандидата, которого не существует, — то есть превращает однозначный случай
в «неоднозначно».

Если `rg` в репозитории нет:

```bash
grep -rn --fixed-strings "ФРАГМЕНТ" src/ \
  --exclude-dir=node_modules --exclude-dir=dist --exclude-dir=build
```

## 2. Ступень 1 — точное совпадение

### Что искать: не `was` целиком, а самый длинный фрагмент без пробелов

Ключевой приём всего документа. `was` **нормализован виджетом**
(`\s+` → один пробел, `trim`), а исходник — нет: там переносы строк, отступы,
неразрывные пробелы, схлопнутые редактором пробелы. Поиск `was` целиком промахнётся
на каждой второй строке, и промах будет выглядеть как «текста нет в исходниках».

Поэтому ищется **самый длинный фрагмент `was`, не содержащий пробелов и кавычек**.
Он переживает любые переносы и схлопывания, потому что внутри него ломаться нечему.

Пример. `was` = `Скорость до 500 Мбит/с, безлимитный трафик`.
Фрагменты: `Скорость`, `до`, `500`, `Мбит/с,`, `безлимитный`, `трафик`.
Самый длинный — `безлимитный` (11 знаков). Им и ищем.

```bash
rg -n --fixed-strings "безлимитный" -g '!node_modules' -g '!dist'
```

Если самый длинный фрагмент короче ~6 знаков или это общее слово («Тарифы»,
«Подробнее»), берите **два фрагмента** и пересекайте списки файлов:

```bash
rg -l --fixed-strings "безлимитный" | sort > /tmp/a
rg -l --fixed-strings "трафик"      | sort > /tmp/b
comm -12 /tmp/a /tmp/b
```

### Экранирование

`was` приходит из чужого текста, и в нём бывает всё: кавычки `"` и `'`, апострофы,
`$`, обратные слэши, скобки, `*`, `.`, `|`.

**Всегда `--fixed-strings` (`-F`), а не регулярное выражение.** Причина не в удобстве:
`.` в регулярном выражении совпадает с любым символом, `500 Мбит/с` без экранирования
найдёт и `500 Мбит-с`, и это будет кандидат, которого не существует, — то есть
нарушение правила 1 руками инструмента.

В командной строке фрагмент берётся в **одинарные** кавычки, если в нём нет
апострофа, и в двойные, если есть:

```bash
rg -n -F 'текст с "кавычками"'
rg -n -F "текст с 'апострофом'"
```

Фрагмент, содержащий и то и другое, передаётся через файл — так кавычки вообще
не попадают в командную строку:

```bash
cat > /tmp/needle <<'EOF'
текст с "обоими" и 'такими' кавычками
EOF
rg -n -F -f /tmp/needle
```

Кавычки вокруг `EOF` обязательны: без них оболочка раскроет `$` и обратные слэши
внутри фрагмента, и искаться будет не то, что вы вставили.

Или, надёжнее всего, выбрать другой фрагмент `was` — без кавычек вовсе. Кавычки
внутри строкового литерала в исходнике всё равно экранированы (`\"`, `&quot;`,
`&#39;`), и точное совпадение по ним не гарантировано.

## 3. Разбор вывода: три случая

### Ноль находок

**Не вывод «текста нет».** Это переход на ступень 2, и только пройдя все пять
ступеней, можно объявить «не найдено».

Прежде чем идти дальше, проверьте фрагмент: не попал ли в него неразрывный пробел
(U+00A0) — визуально он неотличим от обычного, а `--fixed-strings` их различает.

```bash
printf '%s' "$ФРАГМЕНТ" | hexdump -C | head
```

`c2 a0` в выводе — это U+00A0. Тогда фрагмент нужно разрезать по нему: то, что
слева, и то, что справа, ищутся отдельно.

### Ровно одна находка

**Ещё не результат.** Обязателен следующий шаг — чтение файла (раздел 4).
Одна находка означает «такой текст встречается один раз», а не «это то самое место».

### Несколько находок

Смотрите, что именно совпало, и сначала отсеивайте заведомо негодное:
файлы сборки (проскочившие мимо `-g '!…'`), тесты, комментарии, `alt`/`title`,
мета-описания маршрутов. Всё это отсекается чтением, а не догадкой.

Что осталось после отсева и есть список кандидатов для ступени 4. Если их
по-прежнему больше одного — разводить по `contextBefore/After`, `nearestHeading`
и `route`, см. `algorithm.md`.

## 4. Чтение файла после находки — обязательный шаг

Поиск даёт **строку**. Он не даёт **роли**. Одна и та же строка в исходнике может быть:

- живым текстом на странице — единственный годный случай;
- комментарием или закомментированным старым текстом;
- значением `alt`, `title`, `aria-label`, `placeholder`;
- мета-описанием маршрута (`<title>`, `description`, Open Graph);
- фикстурой теста или примером в документации;
- ключом словаря локализации, случайно совпавшим с текстом.

Смотрите достаточно, чтобы понять роль:

```bash
rg -n -F -C 8 "ФРАГМЕНТ" путь/к/файлу
```

`-C 8` — восемь строк вокруг. Меньше — не видно, внутри какого объекта или элемента
лежит строка; больше почти никогда не нужно.

Что вы обязаны увидеть, прежде чем засчитать находку:

1. **Это строковый литерал, а не имя, ключ или атрибут.** `value: 'от 350 ₽/мес'` —
   годится. `alt: 'от 350 ₽/мес'` — нет, правило 2.
2. **Он не в комментарии.** См. следующий раздел.
3. **Его окружение согласуется с `contextBefore` / `contextAfter` / `nearestHeading`**
   записи. Если рядом в исходнике лежат другие строки той же страницы в том же
   порядке — это сильное подтверждение. Если окружение говорит о другом разделе
   сайта — находка, скорее всего, ложная, сколь бы точным ни было совпадение.

### Комментарии и закомментированный старый текст

Строка внутри `//`, `/* */`, `{/* */}` или JSDoc **находкой не является никогда**:
на страницу она не попадает.

Закомментированный старый текст опаснее обычного комментария, и вот почему.
Он совпадает с `was` **точнее живого**: живой текст мог с тех пор поправиться,
а закомментированный застыл на момент, когда его отключили. То есть точное
совпадение здесь — не признак правильного места, а признак устаревшего.

Правило: находка в комментарии отбрасывается, а поиск продолжается. Если
единственная находка оказалась закомментированной — это «не найдено», и в отчёте
так и пишется: «единственное совпадение — закомментированный код».

## 5. Ступень 2 — нормализованное совпадение

Ступень 1 не дала ровно одного кандидата. Причина почти всегда одна: пробелы.

Возможные расхождения между `was` и исходником:

| В `was` | В исходнике |
|---|---|
| один пробел | перенос строки с отступом |
| один пробел | неразрывный пробел U+00A0 или узкий U+202F |
| один пробел | несколько пробелов подряд |
| пробела нет | склейка соседних узлов JSX встык |

Формула нормализации у виджета одна на весь проект: `s.replace(/\s+/g, ' ').trim()`.
Класс `\s` в JavaScript **уже включает** U+00A0 и U+202F — отдельной обработки nbsp
нет, и заводить её не нужно.

Практический приём: поиск регулярным выражением, где каждый пробел `was` заменён
на `\s+`, а спецсимволы экранированы:

```bash
rg -n 'Скорость\s+до\s+500'
```

**`\s` в ripgrep ведёт себя как в JavaScript: он ловит и U+00A0, и U+202F.**
Проверено на `ripgrep 14.1.1` — одинаково в движке по умолчанию и под `-P`.
То есть флаг `-P` здесь не нужен, а одного `\s+` достаточно, чтобы закрыть весь
столбец расхождений из таблицы выше.

> **Не заменять `\s` на `[[:space:]]`.** POSIX-класс неразрывный пробел
> **не ловит** (проверено там же), и подмена превратит рабочую команду в молча
> промахивающуюся — ровно на том случае, ради которого ступень 2 и существует.
> Если движок понимает `\s` по-своему, перечисляйте символы явно: `[ \t\n\r\xA0]`.

Когда фраза длинная и в ней много спецсимволов, надёжнее и быстрее другой путь:
взять два коротких фрагмента без пробелов из **начала и конца** `was`, найти файлы,
где встречаются оба, и прочитать их. Регулярное выражение здесь легко написать
с ошибкой, а ошибка даст ложного кандидата.

## 6. Ступень 3 — поиск по фрагментам

Ступени 1 и 2 промахнулись, потому что строки `was` в исходнике нет **целиком**.
Два случая, и различать их важно.

### Склейка конкатенацией

```ts
description:
  'Мы подключаем частные дома и коттеджные посёлки ' +
  'по всей области, включая удалённые участки, ' +
  'и берём на себя согласование трассы',
```

В DOM это одна строка. В исходнике — три литерала, и ни один не равен `was`.

Как найти:

1. Разрезать `was` по границам слов на 3–5 фрагментов подлиннее.
2. Искать каждый отдельно, собирая списки файлов.
3. Файл, где нашлись **все** фрагменты, — кандидат.
4. **Открыть файл и проверить**, что фрагменты лежат в одном выражении и идут
   в том же порядке, что в `was`.

Шаг 4 не пропускается. Файл, где все фрагменты нашлись в разных, не связанных между
собой местах, кандидатом не является: это совпадение словаря страницы, а не текста.

Слагаемых бывает больше двух — три-четыре обычное дело. Проверив только первое
и последнее, вы рискуете взять цепочку, у которой середина другая.

### Разрыв разметкой JSX

```jsx
<p>Скорость до <strong>500 Мбит/с</strong>, безлимитный трафик</p>
```

`was` = `Скорость до 500 Мбит/с, безлимитный трафик`, потому что виджет склеивает
текстовые узлы всех потомков. В исходнике — три отдельных куска.

Ищется так же, по фрагментам. Отличие — в проверке: нужно убедиться, что куски лежат
**в одном элементе**, а не в двух соседних.

Как отличить одно от другого при чтении файла:

```jsx
<p>Скорость до <strong>500 Мбит/с</strong>, безлимитный трафик</p>   ← один элемент
<p>Скорость до</p><p><strong>500 Мбит/с</strong> трафик</p>          ← два, не кандидат
```

Смотрите на закрывающие теги между фрагментами. Закрылся и снова открылся элемент
того же уровня — это два разных `was`, и ваш относится к одному из них, а не к сумме.

Второй признак: `was` содержит текст, который на странице читается слитно, включая
знаки препинания на стыках (`</strong>, безлимитный`). Запятая, оставшаяся снаружи
тега, — верный признак того, что куски принадлежат одному элементу.

Выписав куски, зафиксируйте адрес каждого — номер строки файла. Он понадобится
при правке: править надо кусок, а не элемент (SKILL.md, «Найден элемент, а править
надо кусок»).

## 7. Проверка «уже применено»

Делается **перед** тем, как объявить запись ненайденной. Те же команды, но искать
надо текст `now`, приведённый к простому тексту (SKILL.md, «`now` — разметка,
а не текст»).

```bash
rg -n -F "ФРАГМЕНТ_ИЗ_NOW" -g '!node_modules' -g '!dist'
```

Разбор вывода:

- **ровно одна находка, роль подтверждена чтением** → запись уже применена ранее,
  раздел отчёта «применено», подраздел «уже было применено ранее»;
- **ноль находок** → запись действительно «не найдено»;
- **несколько находок** → «неоднозначно», а не «уже применено»: правило 1 работает
  и здесь.

Фрагмент для этого поиска берётся по тому же правилу — самый длинный без пробелов
и кавычек, — но из **изменившейся** части `now`. Фрагмент из неизменившейся части
найдёт исходный текст и соврёт «уже применено» по записи, которой никто не касался.

## 8. Порядок, если поиска по коду нет вовсе

Ни `rg`, ни `grep` недоступны — редкий случай, но он бывает в песочницах.
Тогда: перечислить файлы контент-слоя, прочитать их целиком и искать глазами.
Это работает на небольших репозиториях и честно не работает на больших.

В отчёте это указывается в шапке: «поиск по коду был недоступен, просмотрено
N файлов контент-слоя». Молча выдавать неполный обход за полный нельзя —
из отчёта должно быть видно, чему верить.

# Формат обмена «Кальки»

JSON выполняет **четыре роли одновременно**:

1. **Файл сохранения** — то, что лежит в `localStorage` между сессиями рецензента.
2. **Контракт передачи** — то, что рецензент отправляет в мессенджере.
3. **Вход для ИИ-агента** — то, по чему агент правит исходники прототипа.
4. **Тест применения** — тот же файл после передеплоя показывает, что доехало (FR-35).

**Главный потребитель — агент, а не человек** (PRD 1.1, раздел 1а). Читаемость
человеком — вторая задача. Ведущая метрика продукта M7: ≥ 70% правок текста применяются
агентом автоматически. **Любое поле формата оправдано ровно настолько, насколько
поднимает эту долю.**

Бэкенда нет, поэтому файл — единственный носитель состояния. Всего, чего в нём нет,
не существует.

## Схема

```ts
interface ExchangeFile {
  format: 1
  site: string
  author: string
  exportedAt: string          // ISO 8601, UTC
  about: About                // самоописание для агента, FR-45
  entries: Entry[]
}

interface About {
  what: string
  types: Record<EntryType, string>
  rule: string                // «не угадывать»
}

type EntryType = 'text-override' | 'style-wish' | 'comment'
type Entry = TextOverride | StyleWish | CommentNote
```

Тип записи — **ровно один из трёх** (FR-39). Это то, по чему агент решает, применять
запись механически или вынести человеку.

```ts
interface EntryBase {
  id: string
  type: EntryType
  route: string               // FR-40 — без него одинаковые строки на разных страницах неразличимы
  path: string                // FR-43 — «Продукция → карточка 2 → заголовок»
  tag: string                 // FR-42 — 'h3'
  anchor: Anchor              // для виджета, см. kalka-anchoring
  viewport: { w: number; h: number }
  at: string
}

// Применять механически.
interface TextOverride extends EntryBase {
  type: 'text-override'
  was: string                 // нормализованный текст — для поиска
  wasHtml: string             // исходный HTML фрагмента — FR-41
  now: string                 // новый текст, ограниченная разметка
  style?: Style               // сопутствующее пожелание по виду — НЕ применять
  nearestHeading: string      // FR-42
  contextBefore: string       // FR-42, ~100 символов
  contextAfter: string        // FR-42, ~100 символов
  occurrencesOnPage: number   // FR-44 — предупреждение «здесь легко ошибиться»
}

// НЕ применять — вынести на решение.
interface StyleWish extends EntryBase {
  type: 'style-wish'
  was: string
  style: Style
}

// НЕ применять — задача человеку.
interface CommentNote extends EntryBase {
  type: 'comment'
  note: string
  mark: AreaMark | PointMark  // чем помечено место на странице
}

interface AreaMark  { kind: 'area';  rect: { x: number; y: number; w: number; h: number } }
interface PointMark { kind: 'point'; point: { x: number; y: number } }

interface Style { fontSize?: string; color?: string }
```

Имена полей — часть контракта. Менять их без повышения `format` нельзя (NFR-08).

## Три группы полей, два потребителя

| Для чего | Поля |
|---|---|
| **Найти место в исходниках** (агент) | `was`, `wasHtml`, `route`, `path`, `tag`, `nearestHeading`, `contextBefore`, `contextAfter`, `occurrencesOnPage` |
| **Наложить слой в браузере** (виджет) | `anchor`, `viewport` |
| **Понять смысл** (человек и агент) | `type`, `now`, `style`, `note`, `about` |

`anchor` бесполезен агенту — он не открывает браузер. Контекст бесполезен виджету —
у него есть селектор. **Оба набора обязательны, потому что потребителей два.**
Соблазн выбросить «дублирующие» поля — прямой путь к падению M7.

### Что показал замер (спайк R8, 2026-09-04)

Корпус из 15 записей по реальному тексту прототипа заказчика: **12 однозначных находок,
80% при цели M7 ≥ 70%.** Кандидатов было больше одного у шести записей,
разрешились пять.

| Поле | Разрешило | Вывод |
|---|---:|---|
| `route` | 2 | Отсекает конфиги чужих страниц. Бессилен против навигации и подвала: они видны на всех маршрутах |
| `contextBefore`/`After` | 2 | Разводит значения полей внутри одного файла — то, чего `route` и `nearestHeading` не могут |
| `nearestHeading` | 1 | Отделяет заголовок карточки от подписи цифры в шапке |
| `tag` | 0 | **Не используется — и зря**, см. ниже |
| `occurrencesOnPage` | 0 | Флаг осторожности, не средство выбора |
| `path` | 0 | В нынешнем виде не окупается |
| `wasHtml` | — | В поиске не участвует по назначению: сохраняет разметку при применении |

Полей, которые стоило бы **убрать**, замер не нашёл: `route`, `nearestHeading`
и контекст окупились, каждое на своём классе случаев, и ни одно не избыточно
по отношению к двум другим.

### `tag` собран, передан агенту и не используется

Единственная запись замера с исходом «неоднозначно» — строка «Продукция» в шапке.
Два неотсекаемых кандидата: `navigation.ts:23` (`label` пункта меню) и
`home.ts:31` (заголовок секции). `route` бессилен — навигация на всех маршрутах;
`nearestHeading` пуст — над пунктом меню заголовка нет.

При этом в записи уже лежит `tag: "a"`, а второй кандидат рендерится как `h2`.
Различие однозначное, поле собрано, передано — и не читается.

**Что делать:** сверять `tag` с ролью места в исходнике (имя поля и форма
объявления предсказывают роль в разметке: `label` в массиве навигации → ссылка,
ключ `sectionTitles` → заголовок). Правило приблизительное, поэтому применять
его **только для отсечения** кандидата, чья роль заведомо не соответствует `tag`.
Назначать по нему победителя нельзя — это уже угадывание.

По корпусу это подняло бы 12/15 до 13/15: с 80% до 87%.

Как собирается контекст из DOM — в [kalka-anchoring](../kalka-anchoring/references/agent-context.md).

## Почему `style` отдельно от `now`

Решение PRD (раздел 9, риск R4), и в 1.1 у него появилась вторая, более острая причина.

Если оформление подмешать в текст, `now` станет
`<span style="font-size:28px">Краны полярные</span>` — и **агент применит инлайновый CSS
прямо в исходник**. При заданной палитре сайта это не правка, а тема для разговора,
причём разговор состоится уже после того, как изменение попало в код.

**Правило: в `now` никогда не попадают `style`-атрибуты.** Санитизация обязана их
вырезать — см. [references/sanitize.md](references/sanitize.md).

Правка только оформления, без изменения текста, — это отдельная запись `style-wish`,
а не `text-override` с пустым `now`.

## Шапка `about` (FR-45)

Файл должен быть понятен ИИ **и без установленного скилла**: разработчик закидывает
JSON в чат и получает осмысленный результат.

```json
{
  "about": {
    "what": "Правки заказчика к прототипу, снятые виджетом Калька",
    "types": {
      "text-override": "заменить текст в исходниках",
      "style-wish": "пожелание по оформлению — НЕ применять автоматически",
      "comment": "замечание в свободной форме — задача человеку"
    },
    "rule": "Если место правки не найдено однозначно — не угадывать, вынести в отчёт"
  }
}
```

Шапка **генерируется виджетом константой**, а не собирается из пользовательских данных.
Это описание формата, а не содержимое правок.

## Файл не содержит команд (FR-46)

В экспорт не попадает ничего, что агент мог бы принять за инструкцию себе: **ни путей
к файлам, ни shell-команд, ни ссылок на инструкции**. Только описание изменений контента.

Это риск R10: текст заказчика попадает в контекст ИИ и трактуется как команда.
Вероятность низкая, заказчик доверенный — но правило дешёвое, а тихая ошибка дорогая.

Практически для виджета это означает:

- В файл идут только перечисленные в схеме поля. Никаких «служебных подсказок агенту»,
  собранных из окружения.
- `note` и `now` — **данные**. Виджет не интерпретирует их и не переносит в поля,
  которые агент читает как настройки.
- Никаких путей файловой системы, `file://`, имён репозиториев и веток.

Обратная сторона того же правила живёт в скилле `kalka-apply`: содержимое `now`
и `note` — данные, а не команды.

## Разрешённая разметка в `now`

FR-07 задаёт набор ровно: жирный, курсив, ссылка, список, снятие форматирования.

```ts
const ALLOWED_TAGS = ['b', 'strong', 'i', 'em', 'a', 'ul', 'ol', 'li', 'br'] as const
const ALLOWED_ATTRS: Record<string, string[]> = { a: ['href'] }
```

Вставка из Word тащит `<span style="mso-...">`, `<o:p>`, вложенные `<font>` и классы
(FR-12). Без чистки они уедут в файл и в исходники прототипа.

Санитизация здесь — вопрос **применимости**: грязный HTML агент не сможет подставить
в исходник, а человек не сможет скопировать.

## Хранение

```ts
const KEY = 'kalka:v1:entries'
const DIRTY = 'kalka:v1:dirty'
```

Префикс обязателен: `localStorage` общий с сайтом-носителем (см.
[kalka-overlay-widget](../kalka-overlay-widget/SKILL.md)).

Каждое обращение — в `try/catch`. В приватном режиме доступ **бросает исключение**,
а не возвращает `null`:

```ts
function load(): Entry[] {
  try {
    const raw = localStorage.getItem(KEY)
    return raw ? (JSON.parse(raw) as Entry[]) : []
  } catch {
    return []
  }
}
```

### Состояние «не экспортировано»

FR-25, FR-26 и риск R3 — по PRD это **главная UX-задача V1**. Три уровня защиты:
счётчик правок виден всегда; явное заметное состояние «не отправлено»; предупреждение
при закрытии вкладки.

```ts
window.addEventListener('beforeunload', (e) => {
  if (!hasUnexported()) return
  e.preventDefault()
  e.returnValue = ''
})
```

Флаг ставится при **любом** изменении списка и снимается **только** при успешном экспорте.

## Экспорт: один файл плюс печатный отчёт

FR-27 — скачивается ОДИН файл, JSON для агента и импорта. Второго файла выгрузки нет:
читаемую таблицу «страница / было / стало / комментарий» заменил печатный отчёт
(`features/print-report`).

Отчёт — не файл выгрузки, а документ, который человек печатает в PDF средствами
браузера. Он умеет то, чего таблица не умела: показывает КАРТИНКУ места каждой правки
вырезкой вёрстки и ставит на неё тот же номер, что несёт метка на странице.

Устроен он ОПИСЬЮ: одна таблица «№ · Место · Правка», строки в порядке сквозной
нумерации набора, вид правки назван ИНСТРУМЕНТОМ, которым она сделана («Текст»,
«Область», «Указатель»). Разделов по адресату, счётчика «требуют решения» и указаний
читателю в документе нет: он отражает правки, а не распределяет поручения — о чужих
договорённостях он ничего не знает.

Имя файла обмена стоит в шапке нейтральной строкой, рядом с адресом и датой. Это
НЕ смягчение риска «менеджер отправит разработчику один PDF, которым агенту нечего
применять»: прежняя рамка с инструкцией снята сознательно, и риск остался открытым.
Имя названо потому, что без него файл на диске не с чем сопоставить. Набор ещё
не выгружали — строки просто нет, имя не выдумывается.

Имя файла содержит дату и адрес сайта (FR-29). Перед экспортом рецензент видит список
своих правок (FR-28) — не диалог «уверены?», а именно список.

Формат файла и скачивание — в [references/export-import.md](references/export-import.md).

## Импорт и режим проверки

**Импорт накапливает, а не заменяет** (FR-33): файлы от разных рецензентов складываются
в один список с указанием автора. Дедупликация — по паре `(author, id)`.

**Режим проверки (FR-35)** — новое в PRD 1.1. После того как агент применил правки
и стенд передеплоен, тот же файл импортируется снова и служит тестом:

| Что видно в DOM | Значит | Как показать |
|---|---|---|
| `was` не находится, `now` на месте | правка доехала | зелёная |
| `was` всё ещё на странице | правка не доехала | красная |
| ни `was`, ни `now` | место изменилось иначе | требует человека |

Сверка занимает секунды и не требует ручного сравнения списков. Это прямая защита
от риска R9 — тихой ошибки агента.

## Версионирование

`format: 1` — защита от того, что новая версия молча испортит старый файл (NFR-08).

```ts
function parse(raw: string): ExchangeFile {
  const data = JSON.parse(raw)
  if (data?.format !== 1) {
    throw new ImportError('Файл создан другой версией — правки не загружены')
  }
  return data as ExchangeFile
}
```

**Файл с неизвестной версией отклоняется целиком**, а не применяется частично.
Частично применённый импорт — тихая потеря части правок, то есть нарушение Ц4.
Агент обязан вести себя так же.

## Чек-лист

- [ ] `type` — ровно один из `text-override` / `style-wish` / `comment` (FR-39)
- [ ] `route`, `path`, `tag` заполнены у каждой записи (FR-40, FR-42, FR-43)
- [ ] `was` нормализован, `wasHtml` содержит исходный фрагмент (FR-41)
- [ ] `nearestHeading`, `contextBefore`, `contextAfter` собраны (FR-42)
- [ ] `occurrencesOnPage` посчитан (FR-44)
- [ ] Шапка `about` присутствует и сгенерирована константой (FR-45)
- [ ] В файле нет путей, команд и ссылок на инструкции (FR-46)
- [ ] `style` отделён от `now`, в `now` нет `style`-атрибутов
- [ ] `now` санитизируется по белому списку, вставка из Word чистится (FR-07, FR-12)
- [ ] `format` проверяется при импорте, файл чужой версии отклоняется целиком (NFR-08)
- [ ] Ключи `localStorage` с префиксом `kalka:`, доступ в `try/catch`
- [ ] Флаг «не экспортировано» ставится при любом изменении
- [ ] Экспорт даёт ровно один файл обмена, имя содержит дату и адрес
- [ ] Читаемый вывод для человека даёт печатный отчёт, а не второй файл выгрузки
- [ ] Импорт накапливает, дедупликация по `(author, id)`
- [ ] Режим проверки различает доехавшие и не доехавшие правки (FR-35)
- [ ] Записи со статусом `lost` присутствуют в экспорте наравне с остальными

# Якоря «Кальки»

Виджет накладывает правки на **чужую страницу, которую он не контролирует**. Между
моментом, когда рецензент поставил правку, и моментом, когда разработчик её открыл,
страница успевает передеплоиться: классы меняет сборщик, порядок блоков меняет вёрстка,
текст меняет кто-то ещё. Якорь — единственное, что связывает правку с местом.

**Главное правило: якорь может не найтись, и это нормальный, ожидаемый исход.
Молча потерянная правка — дефект. Правка, честно помеченная как «уехавшая», — нет.**

Это прямое требование Ц4 и FR-20/FR-31 из PRD.

## Структура якоря

Якорь — это не один способ найти элемент, а четыре независимых свидетельства о нём:

```ts
interface Anchor {
  selector: string   // CSS-селектор, уровень 1
  xpath: string      // XPath, уровень 2
  snippet: string    // фрагмент исходного текста, уровень 3
  index: number      // какой по счёту среди совпадений по snippet
}
```

Все четыре пишутся **при создании правки**, когда элемент точно под рукой.
Дописать их потом невозможно — элемента уже не будет.

Рядом с якорем запись хранит `was` — полный исходный текст. Он не участвует в поиске,
он участвует в **проверке**: нашли элемент, сверили его текст с `was`, и если не сошлось —
нашли не то. Подробности проверки — в [references/drift-detection.md](references/drift-detection.md).

### Второй потребитель: ИИ-агент

По PRD 1.1 главный потребитель файла правок — не человек, а ИИ-агент, применяющий
правки **в исходниках прототипа**. Браузер он не открывает, и якорь ему бесполезен:
ни селекторов, ни XPath в коде нет.

Поэтому вместе с якорем при создании правки собирается **второй, независимый набор
полей** — `route`, `path`, `tag`, `wasHtml`, `nearestHeading`, `contextBefore/After`,
`occurrencesOnPage` (FR-40…FR-44). Он служит для поиска строки в коде и держит ведущую
метрику продукта M7 (≥ 70% автоприменения).

Оба набора обязательны и собираются одним проходом по DOM —
см. [references/agent-context.md](references/agent-context.md).

## Трёхуровневый поиск

```
1. document.querySelector(anchor.selector)      → нашли? проверить was
2. XPath через document.evaluate                → нашли? проверить was
3. поиск по snippet среди текстовых узлов       → нашли? вернуть с пометкой fuzzy
4. ничего не нашли                              → status: 'lost'
```

> [!done] Стратегия проверена на живом стенде (спайк R1, 2026-09-04)
> 19 наложений за два сценария: SPA-навигация по пяти маршрутам и передеплой.
> **Ноль молча потерянных правок, ноль наложенных на чужой элемент.**
>
> | Уровень | Сработал | Что было бы без него |
> |---|---:|---|
> | 1. Селектор | 14 | — |
> | 2. XPath | 3 | Переименование класса в подвале дало бы `lost` при живом элементе |
> | 3. Фрагмент | 1 | Перестановка блока дала бы `lost` вместо `drifted` |
>
> Третий уровень сработал один раз из девятнадцати — и это не аргумент против
> него. Он стоит одного прохода по текстовым узлам, а взамен превращает потерю
> в помеченную находку.
>
> Решающей оказалась не находка, а **сверка `was`**: у записи, где сменился текст
> заголовка, селектор продолжал работать, и без сверки правка молча уехала бы
> на переименованный элемент.

Уровень считается успешным, только если **и элемент найден, и проверка `was` прошла**.
Найденный элемент с чужим текстом — это не успех, это переход на следующий уровень.

Каждый уровень возвращает не только элемент, но и то, **как** он был найден. Правка,
найденная третьим уровнем, показывается разработчику иначе, чем найденная первым:
третий уровень — это догадка, и человек должен это видеть.

Полные алгоритмы всех трёх уровней — в [references/anchor-strategy.md](references/anchor-strategy.md).

### Уровень 1: CSS-селектор

Строится снизу вверх от элемента к корню, с остановкой на первом уникальном варианте.
Приоритет частей: стабильный `id` → `data-*`-атрибуты → семантический тег →
`:nth-of-type` как последнее средство.

**Не использовать в селекторе** классы, похожие на сгенерированные сборщиком
(`css-1a2b3c`, `_button_x7f2`, хеши). Они меняются при каждой пересборке — селектор
с ними мёртв уже на следующем деплое.

### Уровень 2: XPath

```ts
const r = document.evaluate(
  anchor.xpath, document, null,
  XPathResult.FIRST_ORDERED_NODE_TYPE, null
)
const el = r.singleNodeValue
```

Ключевые факты по MDN:

- Для HTML-документа namespace resolver — `null`.
- Имена тегов в XPath для HTML пишутся **строчными**.
- `FIRST_ORDERED_NODE_TYPE` (9) отдаёт результат через `singleNodeValue`.
- Итераторные типы (4, 5) **инвалидируются при любой мутации документа** —
  а мы мутируем документ, накладывая правки. Использовать только `FIRST_ORDERED_NODE_TYPE`
  или снапшот-типы (6, 7).
- `//foo` сканирует всё дерево. Стройте XPath от корня явным путём.

### Уровень 3: фрагмент текста

Обходим текстовые узлы через `createTreeWalker` с `NodeFilter.SHOW_TEXT`, отсекая
поддеревья самого виджета через `FILTER_REJECT`. Собираем совпадения по нормализованному
`snippet`, берём `index`-е.

Разница `FILTER_REJECT` и `FILTER_SKIP` здесь принципиальна: `REJECT` отсекает узел
**вместе со всем поддеревом** — именно это нужно, чтобы не залезть внутрь собственного UI.
`SKIP` пропустил бы только сам узел и пошёл в детей.

Результат третьего уровня всегда помечается как неточный.

## Геометрия областей

Прямоугольники **не хранятся в пикселях экрана** (FR-18). Рецензент рисует на мониторе
1440px, разработчик открывает на 1920px — пиксельная рамка окажется не там.

Хранится: ссылка на элемент-якорь + смещения в долях его bounding box.

```ts
interface RectAnchor {
  anchor: Anchor
  x: number; y: number; w: number; h: number   // 0..1 от bounding box якоря
}
```

Критично помнить про систему координат: `getBoundingClientRect()` возвращает координаты
**относительно вьюпорта**, и они меняются при прокрутке. Перевод в координаты документа —
прибавить `window.scrollX` / `window.scrollY`. Смешать эти две системы — самая частая
ошибка в этом месте.

Подробности, включая inline-элементы на нескольких строках и `display: none` — в
[references/geometry.md](references/geometry.md).

## Наложение и переприменение

Слой накладывается **после гидрации** (FR-19). Наложиться раньше — значит быть стёртым
фреймворком носителя, когда тот возьмёт DOM под контроль.

Переприменение нужно при клиентской навигации. Ловим её так:

| Способ | Что ловит |
|---|---|
| Патч `history.pushState` / `replaceState` | Программную навигацию SPA — **основной случай** |
| `popstate` | Кнопки «назад»/«вперёд», `history.back/forward/go` |
| `hashchange` | Смену фрагмента `#...` |
| `MutationObserver` | Перерисовку без смены маршрута |
| Navigation API (`navigate`) | Всё сразу — там, где доступен |

**Почему одного `popstate` не хватает:** по MDN `pushState()` и `replaceState()`
**не вызывают** `popstate`. А именно ими SPA и навигирует. Слушать только `popstate` —
значит не увидеть основной сценарий.

**Почему `hashchange` нужен отдельно:** он не срабатывает, если хеш изменили
через `pushState`/`replaceState`.

**Про Navigation API.** Он достиг Baseline Newly Available в январе 2026 (Firefox 147,
Safari 26.2, Chrome/Edge раньше) и ловит навигации, инициированные чужим кодом, — то есть
делает ровно то, что нам нужно, без патча чужих методов. Но «newly available» означает
поддержку только в **свежих** версиях, а рецензент нередко сидит на корпоративной машине
с браузером постарше. Поэтому: **база — патч History API, Navigation API — прогрессивное
улучшение при `'navigation' in window`.** Не наоборот.

Патч чужого `history` — вмешательство в носителя, поэтому он обязан быть аккуратным:
сохранять оригинал, вызывать его всегда, никогда не бросать наружу. Готовая реализация
и правила безопасного патча — в [references/reapply.md](references/reapply.md).

## Ограничения по проекту

- Всё работает **офлайн**: никаких сетевых запросов из кода анкоринга.
- Никаких `console.log` в продакшен-сборке.
- Каждая зависимость расходует бюджет 100 КБ gzip. Для анкоринга внешние библиотеки
  не нужны — всё перечисленное есть в платформе.
- Код анкоринга трогает DOM носителя и потому отделён от кода интерфейса виджета.
- Ошибка внутри анкоринга не должна всплывать в код носителя (NFR-06).

## Чек-лист при работе с якорями

- [ ] Все четыре поля якоря пишутся при создании правки, не позже
- [ ] Контекст для агента (FR-40…FR-44) собирается тем же проходом, что и якорь
- [ ] `was` сохраняется полностью и сверяется при каждом наложении
- [ ] Селектор не содержит сгенерированных сборщиком классов
- [ ] XPath использует `FIRST_ORDERED_NODE_TYPE`, а не итераторный тип
- [ ] Обход текстовых узлов отсекает поддерево виджета через `FILTER_REJECT`
- [ ] Прямоугольники в долях bounding box, не в пикселях
- [ ] Координаты вьюпорта и документа не перемешаны
- [ ] Наложение происходит после гидрации
- [ ] Ловятся `pushState`, `replaceState`, `popstate`, `hashchange`
- [ ] Оригинальные методы `history` сохранены и всегда вызываются
- [ ] Ненайденная правка помечается как «уехавшая», а не исчезает
- [ ] Правка, найденная по фрагменту текста, помечена как неточная
- [ ] В поля для агента не попадают пути, команды и ссылки на инструкции (FR-46)

## Спайк-гейт

PRD (риск R1, этап 0) требует проверить якоря на живом стенде **до начала разработки**.
Проверяются два сценария:

1. **SPA-навигация:** уйти на другой маршрут и вернуться — правки на месте.
2. **Передеплой:** пересобрать стенд и наложить старый файл — уехавшие якоря
   честно помечены, а не потеряны.

Если не проходит — по PRD пересматривается затея, а не дорабатывается реализация.

# Геометрия областей и указателей

Реализация FR-18: прямоугольники хранятся в процентах от bounding box элемента-якоря,
а не в пикселях экрана.

## Почему не пиксели

Рецензент обводит блок на мониторе 1440×900 и получает рамку `left: 320, top: 1180`.
Разработчик открывает тот же стенд на 1920×1080 — вёрстка перекомпоновалась, блок уехал,
рамка осталась на старых координатах и указывает в пустоту.

Поэтому область хранится не «где на экране», а «где внутри вот этого элемента»:

```ts
interface RectAnchor {
  anchor: Anchor              // к какому элементу привязана область
  x: number                   // 0..1 — доля ширины bounding box от левого края
  y: number                   // 0..1 — доля высоты от верхнего края
  w: number                   // 0..1 — доля ширины
  h: number                   // 0..1 — доля высоты
}

interface PointAnchor {
  anchor: Anchor
  x: number                   // 0..1
  y: number                   // 0..1
}
```

Элемент-якорь для области — ближайший к рамке общий контейнер. Он ищется, накладывается
и проверяется теми же тремя уровнями, что и текстовая правка: у области нет собственного
механизма привязки, она наследует его целиком.

## Две системы координат

Главный источник ошибок в этом месте. По MDN:

> `getBoundingClientRect()` возвращает координаты **относительно вьюпорта**, и значения
> `top`/`left`/`right`/`bottom` меняются при прокрутке.

Перевод в координаты документа:

```ts
const rect = el.getBoundingClientRect()
const docLeft = rect.left + window.scrollX
const docTop  = rect.top  + window.scrollY
```

**Правило: смешивать системы нельзя.** Событие мыши даёт обе — `clientX/clientY`
(вьюпорт) и `pageX/pageY` (документ). Выберите одну систему для всего кода геометрии
и придерживайтесь её. Мы работаем во **вьюпортной**: и `getBoundingClientRect`,
и `clientX/clientY` уже в ней, а оверлей позиционируется `position: fixed` — тоже
относительно вьюпорта. Так `scrollX/scrollY` не нужны нигде, и ошибиться негде.

Если оверлей когда-нибудь станет `position: absolute`, вся геометрия переезжает
в координаты документа целиком — половинчатый переход сломает всё.

## Захват

```ts
function captureRect(el: Element, drawn: DOMRect): RectAnchor {
  const box = el.getBoundingClientRect()

  // Вырожденный элемент: делить нельзя.
  if (box.width === 0 || box.height === 0) {
    return { anchor: captureAnchor(el), x: 0, y: 0, w: 1, h: 1 }
  }

  return {
    anchor: captureAnchor(el),
    x: clamp01((drawn.left - box.left) / box.width),
    y: clamp01((drawn.top - box.top) / box.height),
    w: clamp01(drawn.width / box.width),
    h: clamp01(drawn.height / box.height),
  }
}

const clamp01 = (v: number) => Math.min(1, Math.max(0, v))
```

`clamp01` нужен: рецензент может начать рисовать внутри элемента и увести курсор
за его границы. Отрицательная доля или доля больше единицы — валидная геометрия,
но бессмысленное хранилище, и при восстановлении даст рамку за пределами блока.

По MDN `width`/`height` в `DOMRect` включают `padding` и `border-width`. Это ровно то,
что видит рецензент, обводя блок, — дополнительных поправок не требуется.

## Восстановление

```ts
function restoreRect(ra: RectAnchor, el: Element): DOMRect {
  const box = el.getBoundingClientRect()
  return new DOMRect(
    box.left + ra.x * box.width,
    box.top  + ra.y * box.height,
    ra.w * box.width,
    ra.h * box.height
  )
}
```

Пересчитывается **при каждой отрисовке**, а не один раз: bounding box меняется при
прокрутке, ресайзе окна и любой перекомпоновке носителя.

## Пересчёт при изменении раскладки

```ts
function watchLayout(onChange: () => void): Cleanup {
  const onScroll = () => onChange()
  window.addEventListener('scroll', onScroll, { passive: true, capture: true })

  const ro = new ResizeObserver(() => onChange())
  ro.observe(document.body)

  return () => {
    window.removeEventListener('scroll', onScroll, { capture: true } as any)
    ro.disconnect()
  }
}
```

- `passive: true` — обработчик не вызывает `preventDefault`, браузер не тормозит
  прокрутку носителя.
- `capture: true` — ловит прокрутку и внутренних контейнеров, не только окна.
- `ResizeObserver` покрывает и ресайз окна, и перекомпоновку без ресайза.

Отрисовка рамок при этом идёт через `requestAnimationFrame`, а не напрямую из обработчика
прокрутки.

## Пограничные случаи

### Элемент нулевого размера

По MDN: если все border-box элемента пусты, возвращается прямоугольник с нулевыми
`width` и `height`. Деление на такой — `Infinity`/`NaN`, что молча испортит запись.
Проверка `width === 0 || height === 0` обязательна и на захвате, и на восстановлении.

### display: none

Скрытый элемент bounding box на странице не имеет. Правка, чей якорь скрыт, не «уехала» —
она относится к тому, что сейчас не показано (закрытая вкладка, свёрнутый аккордеон).

Такую запись **нельзя** помечать как `lost`: якорь-то нашёлся. Правильное поведение —
не рисовать рамку, но сохранить запись в списке. Иначе разработчик потеряет правку
из-за того, что при импорте у него была свёрнута вкладка.

### Инлайновый элемент на нескольких строках

По MDN `getBoundingClientRect()` для инлайнового элемента, разорванного на несколько
строк, возвращает **объединение** всех строчных прямоугольников. Для ссылки, переносящейся
на вторую строку, это большой прямоугольник, покрывающий и пустое место справа
на первой строке, и пустое слева на второй.

Для рамки-области это приемлемо. Для точной подсветки текста при наведении (FR-05)
берите `getClientRects()` — он отдаёт отдельный прямоугольник на каждую строку.

### CSS-трансформы

`getBoundingClientRect()` отдаёт **фактическую** отрисованную геометрию, с учётом
трансформов. Это желаемое поведение: рецензент обводит то, что видит.

Но осторожно с анимациями: элемент под анимированным `transform` даёт разный bounding box
на каждом кадре. Захват доли в момент, когда анимация на середине, даст неверную долю.
Практически это редкость (обводят статичный контент), но если встретится — фиксировать
как известное ограничение, а не подгонять эвристиками.

### viewport в записи

PRD (риск R5) требует писать в запись `viewport` — размеры окна рецензента в момент правки:

```ts
viewport: { w: window.innerWidth, h: window.innerHeight }
```

В V1 поле не используется при наложении, оно только сохраняется. Нужно оно разработчику:
увидев, что правка сделана при 1440px, он понимает, почему на 375px она выглядит иначе.
Записывать обязательно — задним числом эту информацию не восстановить.

# Сбор контекста для ИИ-агента

Реализация FR-40…FR-44. Новое в PRD 1.1.

## Зачем это отдельно от якоря

Якорь отвечает на вопрос «где этот элемент **в DOM браузера**». Агент браузер не
открывает — он ищет строку **в исходниках прототипа**, где ни селекторов, ни XPath нет.

Поэтому запись несёт два независимых набора полей:

| Набор | Поля | Потребитель |
|---|---|---|
| Якорь | `selector`, `xpath`, `snippet`, `index` | виджет, наложение слоя |
| Контекст | `route`, `path`, `tag`, `was`, `wasHtml`, `nearestHeading`, `contextBefore`, `contextAfter`, `occurrencesOnPage` | агент, поиск в коде |

Выбросить «дублирующий» набор нельзя: `anchor` бесполезен агенту, контекст бесполезен
виджету. Ведущая метрика M7 (≥ 70% автоприменения) держится именно на втором наборе.

**Всё это собирается в момент создания правки.** Дописать потом невозможно — ни элемента,
ни страницы уже не будет.

## Что именно ломает наивный поиск

PRD 1.1 (раздел 10) фиксирует замер на реальном прототипе заказчика. Три способа,
которыми поиск по строке отказывает, и поле, которое спасает:

| Проблема | Как выглядит в коде | Что спасает |
|---|---|---|
| Склейка строк | длинный абзац разрезан конкатенацией `'…' + '…'`; в DOM одна строка, в исходнике куски | поиск по фрагментам — а значит, `was` должен быть полным и нормализованным |
| Дубликаты | одна и та же строка в трёх файлах, включая мета-описание маршрута | `route` + `contextBefore/After` + `nearestHeading` |
| Данные в массивах | `{ value: 'от 350 ₽/мес', label: '…' }` внутри цикла | `path` и контекст, чтобы понять, какое поле объекта |

Плюс нормализация пробелов: неразрывные пробелы и переносы строк в DOM против исходника.

## Полный захват записи

```ts
interface AgentContext {
  route: string
  path: string
  tag: string
  was: string
  wasHtml: string
  nearestHeading: string
  contextBefore: string
  contextAfter: string
  occurrencesOnPage: number
}

function captureContext(el: Element, occurrenceIndex = 0): AgentContext {
  const was = normalize(el.textContent ?? '')
  return {
    route: currentRoute(),
    path: buildPath(el),
    tag: el.tagName.toLowerCase(),
    was,
    wasHtml: el.innerHTML,
    nearestHeading: findNearestHeading(el),
    ...sliceAround(el, 100, occurrenceIndex), // contextBefore + contextAfter
    occurrencesOnPage: countOccurrences(was),
  }
}
```

Та же `normalize`, что используется при сверке `was` в
[drift-detection.md](drift-detection.md). Расхождение между нормализацией при захвате
и при сверке даст правки, помеченные уехавшими на ровном месте, — и агента, который
не найдёт строку, потому что искал не то.

## `was` и `wasHtml` — зачем оба (FR-41)

```ts
was:     'Тарифы на подключение'                        // нормализованный текст
wasHtml: 'Тарифы на <strong>подключение</strong>'       // исходная разметка фрагмента
```

`was` — то, чем агент **ищет**: строка без разметки, с нормализованными пробелами,
такая, какой она вероятнее всего лежит в контент-файле.

`wasHtml` — то, что показывает, **что именно менялось**, когда во фрагменте была
разметка. Без него правка абзаца со ссылкой внутри теряет ссылку: агент заменит текст
и уничтожит `<a>`, никому об этом не сообщив.

Если разметки во фрагменте нет, оба поля совпадают. Это нормально и не повод
выбрасывать одно из них.

## `path` — человекочитаемый путь (FR-43)

```
Продукция → карточка 2 → заголовок
```

Читается **и человеком, и агентом**, и не зависит от вёрстки — этим отличается
от селектора, который после пересборки может указывать не туда.

```ts
function buildPath(el: Element): string {
  const parts: string[] = []
  let node: Element | null = el

  while (node && node !== document.body && parts.length < 4) {
    const label = describeForHuman(node)
    if (label) parts.unshift(label)
    node = node.parentElement
  }

  return parts.join(' → ')
}
```

`describeForHuman` выбирает осмысленное имя: заголовок секции, `aria-label`,
роль элемента («карточка», «заголовок», «кнопка»), порядковый номер среди
однотипных сиблингов. Технические имена — классы, id, теги — в `path` не попадают:
его читает в том числе человек, а по FR-36 он не должен видеть слов «селектор» и «DOM».

Глубина ограничена: путь из десяти звеньев не помогает ни человеку, ни агенту.

> [!warning] В нынешнем виде поле себя не окупает
> Замер R8: `path` не разрешил **ни одного** случая неоднозначности, а качество
> его собственного вывода низкое. Снято на живом стенде:
>
> | Запись | `path` | Что не так |
> |---|---|---|
> | Абзац политики | `Оператор персональных данных → Оператор персональных данных` | Звено продублировано |
> | Вступление на `/products` | `` (пусто) | Ни одно звено не распозналось |
> | Цифра в шапке героя | `Тяжёлые краны и спецтехника для…` | Это H1 страницы, а не путь |
> | Заголовок карточки | `Продукция → ссылка → заголовок` | А вот это как раз хорошо |
>
> Причина в `describeForHuman`: он возвращает пустую метку для `div`, `dl`, `ul`
> и прочих обёрток, поэтому путь то схлопывается, то набирается из чего попало.
>
> **Решение принято вехой «Машиночитаемость для агента» (решение 10), и выбрано
> и то, и другое.** Дефекты вывода починены — `describeForHuman` схлопывает
> подряд идущие одинаковые звенья, распознаёт карточки, списки и заголовки
> и нумерует однотипных соседей, — но `path` признан полем **для человека**,
> и требований по M7 к нему больше не предъявляется. Держать его в одном ряду
> с разрешающими полями нельзя: агент, который ждёт от него выбора места,
> потратит ход впустую. Разрешают неоднозначность `route`, контекст
> и `nearestHeading`.

## `nearestHeading` и контекст (FR-42)

```ts
function findNearestHeading(el: Element): string {
  let node: Element | null = el

  while (node) {
    // Ближайший заголовок выше по дереву или среди предыдущих сиблингов.
    let sib = node.previousElementSibling
    while (sib) {
      if (/^H[1-6]$/.test(sib.tagName)) return normalize(sib.textContent ?? '')
      const inner = sib.querySelector('h1, h2, h3, h4, h5, h6')
      if (inner) return normalize(inner.textContent ?? '')
      sib = sib.previousElementSibling
    }
    node = node.parentElement
  }

  return ''
}
```

Это самое дешёвое поле для разрешения дубликатов: одна и та же строка «Подробнее»
под разными заголовками — разные строки в исходнике.

```ts
function sliceAround(el: Element, chars: number, occurrenceIndex: number) {
  const all = normalize(document.body.textContent ?? '')
  const own = normalize(el.textContent ?? '')

  // Смещение — до НУЖНОГО вхождения, а не до первого.
  let at = -1
  let from = 0
  for (let seen = 0; seen <= occurrenceIndex; seen += 1) {
    at = all.indexOf(own, from)
    if (at < 0) return { before: '', after: '' }
    from = at + own.length
  }

  return {
    before: all.slice(Math.max(0, at - chars), at),
    after: all.slice(at + own.length, at + own.length + chars),
  }
}
```

~100 символов достаточно, чтобы различить два соседних вхождения, и не раздувает файл.

> [!warning] Здесь была ошибка, и она обесценивала поле
> До 2026-09-04 контекст брался как `all.indexOf(own)` — то есть **от первого
> вхождения текста на странице**, независимо от того, какой элемент захвачен.
>
> Проверено на живом стенде (спайк R8): на `/tariffs/connection` строка
> «Тарифы на подключение» встречается трижды — пункт меню, «хлебные крошки»,
> заголовок H1 — и все три записи получали **одинаковые** `contextBefore`
> и `contextAfter`.
>
> То есть поле, существующее ровно для разрешения дубликатов, для дубликатов
> и не работало: неоднозначность вытягивали `route` и `nearestHeading` в одиночку.
>
> **Как это сделано в коде (веха «Машиночитаемость», решение 2).** Никакого
> `occurrenceIndex` нет: обход, строя текст страницы, ЗАПОМИНАЕТ смещение начала
> и конца текста **самого целевого элемента**, и связь с `anchor.index` снята
> целиком — сверять больше нечего, потому что второго счёта нет.
>
> Приравнивать `occurrenceIndex` к `anchor.index`, как советовал образец выше,
> **не надо**: `anchor.index` считает ЭЛЕМЕНТЫ, чей собственный текстовый узел
> содержит фрагмент, а смещение в тексте страницы — это позиция ПОДСТРОКИ.
> Две разные величины: элемент, чей текст разорван вложенной разметкой
> (`<p>Тарифы <strong>льготные</strong> на подключение</p>`), в первый список не попадает
> вовсе, а в тексте страницы его подстрока присутствует. Совпадают они
> на простых случаях и расходятся ровно там, где поле нужно.
>
> В силе осталось другое: текст страницы строится **один раз** за захват,
> и контекст со счётчиком берутся из него оба — три независимые реализации
> одного счёта и есть тот способ получить рассогласование, которым ошибка
> 2026-09-04 и была вызвана. Код: `entities/agent-context/model/occurrences.ts`.

Обход обязан отсекать поддерево виджета — иначе в контекст попадёт собственный
интерфейс. Тот же `WIDGET_ROOT_SELECTOR`, что в [anchor-strategy.md](anchor-strategy.md).

## `occurrencesOnPage` (FR-44)

```ts
function countOccurrences(was: string): number {
  if (!was) return 0
  const all = normalize(document.body.textContent ?? '')
  let count = 0
  let from = 0
  for (;;) {
    const at = all.indexOf(was, from)
    if (at < 0) break
    count++
    from = at + was.length
  }
  return count
}
```

Поле — **прямое предупреждение агенту**: «здесь легко ошибиться». При значении больше
единицы агент обязан опереться на `contextBefore/After`, `nearestHeading` и `tag`,
а если и они не разрешают неоднозначность — не угадывать, а вынести в отчёт.

> [!note] Это флаг осторожности, а не разрешающее поле
> Замер R8 (15 записей): `occurrencesOnPage` не разрешил **ни одного** случая
> неоднозначности — и по устройству не может, это число, а не признак места.
> Разрешали `route` (2 случая), `contextBefore/After` (2) и `nearestHeading` (1).
>
> Польза у него другая и вполне реальная: он один раз поймал расхождение
> «в DOM строка одна, а кандидатов в исходниках несколько» — сигнал, что
> захват и индекс смотрят на разные вещи.
>
> Держать его в одном ряду с разрешающими полями не следует: агент, который
> ждёт от числа выбора места, потратит на него ход впустую.

Считается по нормализованному тексту всей страницы, а не по совпадениям селектора:
агенту важно, сколько раз строка встречается **как текст**, потому что именно так
он её и будет искать в исходниках.

### Связь с `anchor.index`

`anchor.index` (сколько таких же фрагментов **до** элемента) и `occurrencesOnPage`
(сколько их **всего**) считаются одним проходом и по одной нормализации. Разводить
их на две независимые реализации — верный способ получить рассогласование.

## Чего в контексте быть не должно (FR-46)

В собираемые поля **не попадает ничего, что агент мог бы принять за команду**:
ни путей файловой системы, ни имён репозиториев и веток, ни URL с инструкциями,
ни «подсказок агенту», собранных из окружения страницы.

Контекст — это **описание места на странице**, и только оно. `path` строится из
человекочитаемых меток, `contextBefore/After` — из текста страницы, `nearestHeading` —
из заголовка. Ни одно из полей не читает окружение разработчика.

Это риск R10 из PRD: текст попадает в контекст ИИ и трактуется как инструкция.

## Чек-лист

- [ ] Контекст собирается в момент создания правки, вместе с якорем
- [ ] `was` и контекст используют ту же `normalize`, что и сверка при наложении
- [ ] `wasHtml` сохраняет разметку фрагмента, если она была
- [ ] `path` не содержит технических терминов и ограничен по глубине
- [ ] `nearestHeading` ищет и выше по дереву, и среди предыдущих сиблингов
- [ ] `contextBefore/After` около 100 символов, поддерево виджета отсечено
- [ ] `occurrencesOnPage` и `anchor.index` считаются согласованно
- [ ] В контекст не попадают пути, команды и ссылки на инструкции
